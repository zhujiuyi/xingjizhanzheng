# 星际战舰 · 数据库与存读档技术方案

日期：2026-10-04 更新。SQLite 路线、实际 Store/存读档服务及完整单人玩法已实现，Mac 与 Windows 客户端均已原生验收。本文保留总体架构；精确表名/约束见 [18](18-进度数据库与存档实现规格.md)，当前运行与验收证据以 [24](24-数据服务实现与验证.md) 和 [26](26-开发阶段与交付记录.md) 为准。

## 1. 已确认要求与本方案建议

已确认：主技术栈为 **Godot 4 标准版 + typed GDScript + Forward+ + Blender**；以 macOS `.app`、Windows `.exe` 独立客户端提供 3D 星际探索、采矿和战斗；只供自己与朋友玩，控制开发成本，不采用收费授权技术栈。用户进一步要求：**用数据库实现存档、读档，并用数据库管理数值配置。**

本轮新增内容纳入数据范围：多星系特色及独有产出、不同势力的舰船 / 武器 / 装甲科技、固定锚定虫洞传送门、风险分区及 NPC 等级、研究、蓝图、制造、商店和掉落。高 / 中 / 低安全区 NPC 等级区间初稿为 **1–5 / 3–8 / 6–12**；这是待平衡的初稿，不构成已验证难度结论。

**本项目采用 SQLite + godot-sqlite GDExtension**，作为用户已批准路线与完整开发准备授权下的工程实现选择。先实现离线存读档，再复用同一持久化层支持可选的朋友房主联机；不把专用服务器、云数据库或付费服务作为前提。

SQLite 是嵌入式 SQL 数据库引擎，虽然物理载体是 `.db` 文件，仍有表、索引、约束和事务，符合数据库要求。它不需要单独数据库服务进程，数据格式可跨平台使用。[SQLite 官方介绍](https://www.sqlite.org/about.html)

本方案的运行时权威数据为数据库：数值定义在 `catalog.db`，持久化进度在 `progress.db`。JSON、Godot `.tres` / `.res`、场景文件和对象序列化包不作为权威数值配置或权威存档。模型、材质、纹理、声音、动画、场景与 Shader 仍作为资产文件；数据库记录稳定资产标识和必要路径，不把大块媒体塞进数据库。

v0.2 审核补充：用户已确认先做单人闭环，保留联机数据与接口。[数值基线](15-数值系统与平衡基线.md) 维护当前数值资产，[首版实现契约](17-首版行为与实现契约.md) 明确动作、停靠、保障、跨区及耐久语义。

### 2.3 当前 WAL 版本风险与选择

SQLite 官方披露：`3.7.0` 至 `3.51.2` 存在罕见的 WAL-reset 问题，可能损坏数据库；触发条件涉及同一 WAL 数据库在不同线程或进程中有多个连接同时写入或执行 checkpoint。`3.51.3` 及之后版本修复，部分旧分支也有回补。作者 v4.9 发布说明标称的 `3.51.0` 落在该版本范围内，是否另有回补尚未验证。[SQLite 官方 WAL-reset 说明](https://www.sqlite.org/wal.html#walreset)

因此建议初版使用 **单连接写入队列 + `journal_mode=DELETE` + `synchronous=EXTRA`**。存档低频写入，无需为尚不存在的并发读写需求先引入 WAL。若后续确需 WAL，先取得包含修复的扩展构建，核验运行时版本及修复证据，再做并发与备份测试。不能仅因扩展发布较新就认为其内嵌 SQLite 已修复。

`EXTRA` 相比 DELETE 模式下的 `FULL` 增加目录同步，以提高刚提交事务面对断电的耐久性；实际开销待测。硬件、文件系统或存储损坏仍可能导致数据丢失，数据库事务不能代替备份。[SQLite 同步模式说明](https://www.sqlite.org/pragma.html#pragma_synchronous)

## 3. 两库职责与路径

以下区分已交付工程资产与运行时创建的位置。

| 数据 | 建议位置 | 权限与职责 |
| --- | --- | --- |
| 默认数值库 | `code/data/catalog.db`，运行时 `res://data/catalog.db` | 随版本交付；游戏以只读方式打开；含舰船、装备、矿物、任务、星区等定义 |
| 玩家进度库 | 运行时 `user://database/progress.db` | 本机可写；含世界、玩家、存档槽、状态快照及冻结的内容定义副本 |
| 数据库迁移及初始化 SQL | `code/database/catalog_schema.sql`、`catalog_seed.sql`、`code/database/progress/` | 正式工程的一部分；用于可审查、可重建的表结构和初始数值，不另造 JSON 数值来源 |
| 运行备份 | `user://database/backups/` | 有保留策略的完整数据库备份；不作为常规存档槽 |
| 测试库、故障注入与工具脚本 | `jiaoben/`，临时产物在 `jiaoben/tmp/` | 不混入正式数值库或发布资源 |

`user://` 对应 Godot 为应用提供的用户数据目录。客户端界面提供“打开存档目录”，不要在代码中固定开发机的绝对路径。朋友首次运行时创建进度库，不向安装包、`res://` 或 `.app` 内写进度。

扩展提供只读打开以及 PCK 内数据库的读取能力；发布时应明确把 `.db` 纳入导出资源过滤，不能假设 Godot 会自动包含所有非资源扩展名文件。可写库放用户目录。[作者 README 的路径、只读与导出说明](https://github.com/2shady4u/godot-sqlite#variables)

两个库使用独立连接。初版不依赖 `ATTACH` 或跨库写事务：数值库固定只读，全部存档写入只发生在 `progress.db`。SQLite 外键不能跨 schema；即使 `ATTACH` 另一个数据库，也不能建立跨库外键。WAL 下多库事务也不具有整体崩溃原子性。[SQLite 外键限制](https://www.sqlite.org/foreignkeys.html#fk_unsupported)、[ATTACH 事务边界](https://www.sqlite.org/lang_attach.html)

世界层级按“星域 → 星系 → 局部星区 / 地点”组织；初版可让一个星系只有一个主要星区场景，表结构仍保留一星系多星区关系。当前数据提案的主要星区 ID 为 `sector_anchor`、`sector_echo`、`sector_mirror`、`sector_forge`、`sector_iron`、`sector_helios`、`sector_drift`、`sector_mist`、`sector_rift`、`sector_silent`；势力 ID 为 `faction_route_council`、`faction_deepforge`、`faction_roaming_alliance`、`faction_silent_relics`；统一货币为 `currency_route_credit`（航路信用点）。这些是待落库的稳定引用提案，不表示已有数据库记录。

### 4.2 类型、单位与校验

- 信用点、数量、堆叠与容量计费使用整数或约定的最小整数单位，避免浮点累计造成交易误差。移动、方向、时间、距离等使用 `REAL`，明确米、秒、弧度等单位。
- 每个业务主键和必要字段同时设置主键 / 唯一性及 `NOT NULL`；不要仅靠 typed GDScript 推断数据库类型。推荐使用 `STRICT` 表，并在扩展实际支持的 SQLite 版本上验证。
- 用 `CHECK` 表达单行范围，如 `quantity > 0`、`shield_max >= 0`、合法状态枚举；父子关系使用本库外键；为常查外键和检索字段建索引。跨行概率和、装备容量总和、任务目标类型匹配等由内容构建检查与运行服务验证。
- 进入游戏前验证所有 ID、资产引用、有限浮点值及范围；禁止 NaN / 无穷值、负库存、无效星区、无效舰船类型进入内存模型。错误精确到表、ID 与字段，不静默采用硬编码默认数值。
- SQL 参数使用绑定；表名、列名、排序字段来自代码白名单。绑定参数不能代替 SQL 标识符校验。运行时不开放动态 SQLite 扩展加载。

数值调优通过事务修改开发用数据库，并保存相应初始化 SQL / 数据迁移差异以便审查重建。构建阶段校验并生成只读 `catalog.db`；游玩过程中不直接编辑交付库。表结构、数值内容版本和游戏规则代码版本分别管理，避免一个版本号混合三种变化。

## 5. 内容版本与冻结定义

只在存档写一个版本字符串不足以恢复旧数值；同名版本可能被重建，定义也可能被删除。新世界创建时，把所选完整内容定义集从只读 `catalog.db` 复制到 `progress.db` 的冻结定义表，建立 `content_snapshot`。

冻结定义仍是关系表，如 `frozen_ship_def`、`frozen_module_def`、`frozen_item_def`、`frozen_sector_def`，以 `(content_snapshot_id, definition_id)` 为主键；不转换成 JSON 大字段。初版内容规模小，复制完整定义集比计算只复制“已使用内容”的引用闭包更容易保证后续任务、解锁与掉落可用。相同内容摘要的世界可复用一份冻结定义。

`content_snapshot` 至少保存：内部 ID、`pack_id`、`content_version`、`catalog_schema_version`、`ruleset_version`、规范化内容摘要、创建时间。摘要按规定顺序遍历定义记录计算，避免数据库页布局、VACUUM 或构建时间变化影响逻辑内容身份。

创建新世界时，定义副本、世界元数据及初始存档在 `progress.db` 的同一事务中写入。建立完成后冻结定义禁止普通游戏服务修改。加载旧世界从其冻结定义恢复，而不是随客户端更新自动套用新的 `catalog.db`。改变世界规则需显式内容迁移并先备份，产生新的内容快照与存档；已有手动存档继续指向原快照。

此结构还解决跨库外键问题：存档实体通过复合外键指向**进度库内**同一 `content_snapshot_id` 的冻结定义，而不是声称可外键引用只读数值库。发布库到冻结副本的一致性由复制事务与摘要校验保证。

定义快照保存数值及资产引用，不复制所有模型和音频，也不能冻结游戏代码。旧资源被移除或规则代码不兼容时，即使数值存在也可能无法加载；客户端需保留受支持版本所需资产，或提供明确迁移 / 兼容拒绝，不静默替换。资源版本、规则版本及存档格式版本均进入兼容检查。

## 6. 进度库、存档槽与运行会话

### 6.1 三个不同概念

| 概念 | 含义 | 持久化方式 |
| --- | --- | --- |
| Session | 本次运行中的世界，含运行时舰船、AI 与任务状态 | 主要存在内存；临时 `session_id` 和 `session_epoch` 区分不同读档后的会话 |
| Save snapshot | 某一个一致模拟时刻的完整世界快照 | 关系表内的不可变记录，所有状态按同一个 `snapshot_id` 组织 |
| Save slot | 用户看到的手动档 / 自动档入口 | 槽元数据和指向完整快照的引用；覆盖存档通过原子替换该引用实现 |

初版建议 5 个手动槽、3 个轮转自动槽和 1 个独立快速槽；这是可调整的工程默认值，不是用户已确认数量。每个槽显示世界名称、游戏时间、保存时间、所在星区、主控舰船及内容版本。手动槽不会被自动档覆盖，最近一次成功档始终保留。

不要把 SQLite `SAVEPOINT` 当作玩家存档槽。它只是事务内的局部回滚机制，不是关闭应用后可加载的游戏保存点。

### 6.2 关系模型建议

| 表 | 必要字段与主键 | 说明 |
| --- | --- | --- |
| `database_meta` / `migration_history` | 格式版本、应用标识、迁移序号、迁移摘要、完成时间 | 独立于内容版本；启动判断数据库是否属于本游戏及是否可读 |
| `profile` | `profile_id`、显示名、创建时间 | 本地档案；不伪装成互联网身份认证 |
| `world` | `world_id`、模式、世界种子、初始 / 默认内容快照 ID、创建时间 | 离线与房主世界复用该模型；每档使用的实际版本由该档独立绑定 |
| `save_snapshot` | `snapshot_id`、`world_id`、`content_snapshot_id`、`ruleset_version`、`parent_snapshot_id`、保存原因、UTC 时间、模拟 tick、累计游戏时长、RNG 状态 | 不可变完整快照；旧手动档继续绑定旧定义；同一世界中的实体 ID 跨快照稳定 |
| `save_slot` | `slot_id`、`profile_id`、`world_id`、槽类型、序号、标签、`current_snapshot_id`、更新时间 | `(profile_id, world_id, slot_type, slot_index)` 唯一；指针必须属于同一世界 |
| `player_state` | `(snapshot_id, player_id)`、主控舰船实例 ID、信用点、解锁状态关联、可恢复镜头模式 | 单机保留一个玩家；朋友加入后按稳定玩家 ID 保存；镜头模式与个人画质偏好分开 |
| `ship_state` | `(snapshot_id, ship_instance_id)`、拥有者、冻结舰船定义 ID、星区 ID、局部位置、姿态、线 / 角速度、船体 / 装甲 / 护盾 / 能源、温度、状态 | 实例与定义分开；保存可恢复状态，不存 Godot Node 的路径或临时实例编号 |
| `container_state` | `(snapshot_id, container_id)`、容器类型、拥有者、所属舰船/站点或合法挂点 | 仓库、货舱与安装位置具有稳定标识；固定站点关联定义，移动容器关联实例；类型决定可接收内容 |
| `item_instance_state` | `(snapshot_id, item_instance_id)`、冻结物品/模块定义 ID、当前容器 ID、确定品质结果、耐久、制造批次/改装状态 | 不可堆叠装备独立存实例；无论在仓库、货舱还是安装位都保留属性；每个实例只指向一个合法位置 |
| `equipment_state` | `(snapshot_id, ship_instance_id, slot_index)`、装备实例 ID、剩余冷却、开关状态 | 外键关联同一快照的舰船与独立物品实例；安装容器与挂点关系一致；不重复维护另一套品质/耐久；兼容与容量由服务校验 |
| `inventory_state` | `(snapshot_id, container_id, stack_id)`、冻结物品定义 ID、整数数量 | 保存可堆叠货物；不可堆叠实例由独立物品表定位，不能用“模块类型 + 数量”抹掉品质和损伤 |
| `mission_state` / `mission_objective_state` | 快照、玩家、任务实例及定义 ID、状态、步骤进度、奖励领取状态 | 已领取奖励不能因重复请求再发放；记录任务实例，不只记录任务模板 |
| `loan_state` / `asset_origin_state` | 快照、教学借用合同 ID、当前有效船/模块实例、领取/归还/损毁/换发状态；保障/借用/任务样本来源与允许交付目标 | 专业借船已毁可换发，不重复奖励；标签随拆装保留，普通商品与受限资产分开，避免重复领取和教学死锁 |
| `sector_state` / `entity_state` | 快照、星区、资源点 / NPC 等稳定 ID、资源余量、销毁 / 占用状态、重生剩余时间 | 未加载星区仍保留变化；静态内容可由种子与冻结定义重建 |
| `discovery_state` / `unlock_state` | 快照、玩家、发现对象 / 解锁定义 ID | 集合记录用唯一键防重复 |
| `reputation_state` / `world_event_state` | 快照、玩家/势力、声望值；世界事件实例、阶段与剩余时间 | 影响合同、服务与门状态的世界变化随存档恢复，避免只恢复资产却保留未来事件 |
| `research_state` / `production_state` | 快照、玩家、研究 / 制造任务实例、冻结定义 ID、剩余时间、已投入材料、完成 / 领取状态 | 已消耗与已产出明确；加载不能重复扣料或发产物 |
| `shop_state` / `shop_stock_state` | 快照、商店实例及定义 ID、所在星区、商品整数库存、当前成交价、补货剩余时间 | 动态库存和价格随世界回档；仅计算不落库的临时询价不视为已成交 |
| `gate_state` | 快照、固定门 ID、已发现 / 解锁等世界状态、必要冷却剩余时间 | 拓扑引用冻结定义；初版无需的动态占领等字段不提前实现 |
| `processed_action` | 快照或当前会话、请求 ID、动作类型、结果引用 | 可选房主联机去重；读档恢复对应快照或重建新会话，不能沿用被回退的未来交易记录；不是逐帧无限追加的全量事件日志 |

状态表均用相同 `snapshot_id`，不得混用上一档库存与下一档任务结果。通过复合唯一键和外键保证“同一世界、同一内容快照、同一存档快照”关系，避免仅靠应用层约定。库存、任务奖励与信用点在一个保存事务中提交。

未安装装备同样是可持久化实例。实例位置只维护一个权威容器引用；安装时将其移到对应挂点容器并建立运行设备状态，拆卸时移回仓库/货舱并清理安装关系。约束与业务校验禁止同一实例同时在仓库、运输、挂点或交易交付位置出现；堆叠数量与非堆叠实例数量不能双重计入资产。

需要引用冻结定义的状态行携带对应 `content_snapshot_id`，并同时校验 `(snapshot_id, content_snapshot_id)` 属于其保存快照、定义 ID 属于该内容副本。读档以 `save_snapshot` 的内容绑定为准，不用世界当前默认版本覆盖旧档；这样显式迁移后的新档与原手动档才能共存。

个人存档允许手动回档：信用点、库存、矿点余量、掉落、研究 / 制造、商店库存与任务领取等一起恢复到所选时间点。**本地经济可随存档回退，不宣称不可回退或防修改。** 请求去重防止当前会话中的重发造成重复执行，不应被解释成读旧档后仍强制保留未来交易。合作世界只有房主保存和读档，整个世界与参与玩家状态一起回退，不做各玩家独立资产回档合并。

位置保存为 `sector_id + local_x / local_y / local_z`；姿态保存明确顺序的四元数分量，并校验归一化；速度以米每秒保存。世界种子及必要 RNG 状态可用整数或有版本的少量二进制字段保存，不将全世界编码为不透明 BLOB。计时器保存剩余模拟秒数，离线是否继续重生作为规则明确决定，不能由系统时钟差值隐式改变玩法。

瞬时粒子、音源播放游标、屏幕震动、GPU 状态和正在飞行的纯视觉碎片不存入数据库。初版在稳定阶段存档；若以后允许战斗中保存，需显式补齐有效投射物、AI 状态、锁定目标和冷却，不能承诺任意时刻无损恢复。

个人画质、镜头强度、音量与操作偏好可存于独立的进度库设置表，不随世界回档；这些记录与世界快照分开。固定媒体资产几何参数不属于平衡数据库范围；影响玩法或可调表现的数值遵循数据库定义。

## 7. 原子存档与读档流程

### 7.1 初始化与新世界

1. 核验只读数值库和原生扩展可用；可写库不存在则创建，有库则先检查格式和迁移状态。
2. 在连接打开前启用扩展的外键选项，打开后查询 `PRAGMA foreign_keys` 必须得到启用结果；设置并回读日志、同步模式等配置。
3. 创建世界时校验所选定义集，形成只读的内存初始状态；在一个写事务中复制冻结定义、建立世界并写入初始快照与槽指针。
4. 全部提交成功后进入游戏；失败则回滚，保留错误与可重试入口，不留下指向半成品的槽。

SQLite 外键需为每条连接明确启用，不能依赖默认值；事务进行中切换外键开关不会生效。[SQLite 外键启用说明](https://www.sqlite.org/foreignkeys.html#fk_enable)

建议连接初始化值：`foreign_keys=ON`、`journal_mode=DELETE`、`synchronous=EXTRA`、有限的 `busy_timeout`。等待上限初拟 2 秒，在数据库拥有者线程内使用；主线程不能因数据库忙而无提示卡住该时长。具体性能和超时数值须通过实际原型调整。

### 7.2 存档

1. SaveService 受理手动、快速、自动或退出请求，分配唯一请求 ID；已有相同请求则去重。
2. 在一个模拟 tick 结束的稳定边界捕获完整内存状态，复制成不可变的类型数据对象。初版离线可短暂停顿；虫洞中、场景仍未初始化或奖励操作尚未完成时延后，不读取持续变化的 Node 拼凑快照。
3. 把快照、目标槽、会话代次、内容快照 ID 放入单一写入队列；只有数据库拥有者执行 SQL。
4. 使用 `BEGIN IMMEDIATE`，插入新的 `save_snapshot` 及其全部状态行，验证必需记录与引用，再更新槽指针和必要的元数据；所有 SQL 使用参数绑定。
5. 检查每个步骤及 `COMMIT` 返回值。任一失败明确执行回滚；事务未完成前不显示“保存成功”，旧槽指针继续可用。
6. 提交完成后通知界面成功。自动档轮转和旧快照清理遵循保留策略，不能先删上一档再尝试保存新档；清理失败不撤销已成功的存档。

SQLite 同时只允许一个写事务；`BEGIN IMMEDIATE` 可提前取得写事务，失败时可能返回忙。提交失败也不能当作成功；根据明确错误状态重试或回滚，不盲目重放已提交的奖励逻辑。[SQLite 事务文档](https://www.sqlite.org/lang_transaction.html)

这里的原子性指同一 `progress.db` 内“完整状态 + 槽指针”一起提交或一起回滚。它不包含镜头动画、网络消息、外部截图文件或另一数据库；缩略图失败不能使有效存档不可读取。

### 7.3 读档

1. LoadRequest 携带 UI 选定的快照 ID 和槽 generation；先建立加载屏障，暂停新保存/世界变更，取消未开始请求并等待已开始 SQL 完成。保留原世界和 session epoch。
2. 核对槽 generation，已改变则返回 `STALE_SELECTION`；固定目标快照后在同一读事务中读取冻结定义和全部状态，完成后尽快结束事务，避免锁跨场景加载。
3. 检查格式 / 规则 / 资源版本、必需表与字段、世界及定义引用、数值范围、任务领取一致性；构造独立待加载状态，不边读边修改现有游戏世界。
4. 在加载界面准备目标星区和资产。准备失败保留原会话，或者返回菜单并提供其他槽 / 备份选项；不覆盖原数据库。
5. staging 全部就绪后，才以 CAS 原子推进 `session_epoch` 并切换运行世界。准备失败不推进 epoch，释放屏障继续原会话；不能先使旧会话失效再尝试加载。重建规则与切换边界详见18/21。
6. 旧会话任务即使随后回调，也因代次不匹配被丢弃，避免读档后旧自动保存覆盖槽。只有新会话再产生保存请求时才创建新的快照。

常规读档仅加载指定关系快照，不调用插件的 `restore_from()` 覆盖整个 `progress.db`。后者适用于完整数据库恢复，会覆盖其他槽与世界；不能把“读一个存档槽”实现成“抹掉全部进度库”。

### 7.4 自动档与退出

建议自动档触发点为返回安全区域、交付任务事务完成、跳跃后的目标星区初始化完成，再加低频定时触发；定时初拟 5 分钟，待实际保存耗时调整。连续触发合并为一次最新快照，手动请求保留优先级。退出时等待正在写入的事务完成并明确展示状态；强制关闭只保证上次成功提交的档可恢复，不保证最后一帧保存。

## 8. 数据访问、写入队列与运行内存

| 服务 | 职责 |
| --- | --- |
| `DatabaseAdapter` | 隔离 SQLite 扩展对象；统一打开、关闭、绑定查询、事务、错误与版本查询 |
| `CatalogRepository` | 读数值定义与冻结副本，转换为 typed GDScript 定义对象，校验引用 |
| `ProgressRepository` | 写完整快照、读指定快照、管理槽与关系约束 |
| `SaveService` | 快照捕获、请求去重、队列、会话代次、成功 / 失败通知 |
| `MigrationService` / `BackupService` | 版本迁移、备份验证、恢复与保留清理；与正常存档分开 |

数据库只保存持久状态。进入世界 / 星区时把需要的定义和状态读入内存；飞行物理、瞄准、伤害计算、采矿循环、AI 与特效更新使用内存对象。**不在 `_process()` / `_physics_process()` 中逐帧查询或写入数据库。** 玩家奖励先在模拟边界完成一致内存变更，再由快照保存保证数据库一致性。

制造/交易/采矿文档中的“业务事务”统一指有 `action_id` 的原子内存变更；全快照 SQL 事务才是磁盘耐久边界。业务完成可以请求自动保存，但不能在提交完成前声称已经保存。跨区使用 origin 自动档、准备目标、destination 候选完整快照提交、再替换运行世界的顺序，费用及门状态随目的地快照一起提交；失败和强退只恢复已提交的完整端点。具体可保存条件、延后与取消规则见实现契约。

初版用一条串行队列拥有进度库连接；读取、保存、备份与迁移均经过该拥有者。建议由单独数据库线程创建、使用、关闭该连接，主线程只捕获 / 应用类型数据对象；不得跨线程共享同一个插件对象，也不得在工作线程操作场景树。扩展在工作线程的行为必须实测，不把“SQLite 支持线程”直接等同于“Godot 扩展所有接口可任意并行”。若初版暂未完成线程验证，先在稳定加载 / 暂停阶段执行短事务并测量卡顿，不在战斗帧内同步保存。

队列有容量上限；重复自动保存可以合并，手动保存与迁移不得被静默丢弃。失败给出可重试原因；数据库忙有限重试，磁盘满 / 权限失败不能无限等待。相同进度目录避免两个客户端实例同时游玩写入；遇到已占用则拒绝第二个写入会话或切换独立档案，不把无限等待当作互斥策略。

## 9. 离线与可选朋友房主联机

| 模式 | 数据库所有者与保存责任 | 边界 |
| --- | --- | --- |
| 离线 | 本机拥有世界与 `progress.db`，SaveService 保存全部状态 | 无网络依赖；玩家可在本机选择槽及回退 |
| 朋友房主联机 | 房主模拟并保存完整世界及参与玩家状态；加入者发送操作请求 | SQLite 留在房主本地；房主程序承担权威角色，不要求租用服务器 |
| 加入者本机 | 可保存本机设置；世界进度以房主版本为准 | 不向房主传任意 SQL，不以加入者库存 / 钱包库覆盖房主世界 |

联机时保留世界 ID、稳定玩家 ID、内容摘要与网络协议版本握手。客户端与房主内容不一致则拒绝加入或进入明确的兼容流程；不能只比显示版本字符串。任务完成、奖励、掉落和装备变更由房主校验，必要动作使用请求 ID 去重，防止重发导致多次发放。

房主存档应在统一模拟 tick 捕获所有参与者的一致状态；数据库写盘可排队，不能只保存房主舰船。读档由房主发起，暂停 / 重建会话并让玩家重新同步；加入者不能单独回退同一世界的一部分。房主离开后会话结束，初版不做自动房主迁移或跨玩家存档合并。

如需把世界交给另一位朋友，退出后通过受控“导出世界 / 导入为新世界”流程交换完整且验证过的数据库副本，重建所有权；不让多台机器在网络共享目录、同步盘或 SMB 上同时打开同一进度库。公网连接、NAT 或可选中继另行处理，与数据库选型分开。

## 10. 备份、WAL、副本与迁移

### 10.1 正常备份与恢复

存档槽是玩家时间点，数据库备份是进度库整体的恢复副本，二者分开。建议迁移前必备份；平时保留最近若干次成功备份和少量按日期备份，具体空间预算待测。

作者扩展提供 `backup_to()` / `restore_from()`。备份优先通过 SQLite Backup API 形成一致数据库副本，而不是在连接仍写入时直接复制 `.db`。[扩展备份接口](https://github.com/2shady4u/godot-sqlite#methods)、[SQLite 官方 Backup API](https://www.sqlite.org/backup.html)

备份写到同一目录的唯一临时路径，成功后打开副本验证应用标识、格式版本、`PRAGMA quick_check`、外键及关键槽引用，再发布为正式备份并更新保留记录；失败不覆盖现有好备份。完整性检查只能发现其覆盖范围内的问题，不能证明平衡数值或全部游戏语义正确。

恢复前停止模拟与队列、保留当前库副本、验证候选备份，再关闭或隔离现有连接并替换 / 恢复。失败保持原库及备份；不要在活动会话中对正被使用的数据库调用全库覆盖。读取槽继续采用第 7 节流程。

### 10.2 未来启用 WAL 时必须遵守

- 启用前先满足第 2.3 节修复版本条件；仍使用单一写入拥有者，WAL 不会增加 SQLite 同时写事务数量。
- WAL 的已提交内容可能仍在 `progress.db-wal`，不能只复制 `progress.db` 就认为拿到了最新完整档；不要手工删除 `-wal`。`-shm` 是共享内存索引，也应由 SQLite 管理。
- 在线备份优先用 Backup API，避免自行同时复制三个活动文件；冷备份需停止所有访问，确认 checkpoint 完成并正常关闭连接后再复制，不能把“发出 checkpoint 命令”当作已完成。
- 长时间读事务会影响 checkpoint 和 WAL 回收；读档先读入内存再结束事务，不保持数据库游标跨越场景加载或网络等待。checkpoint 放在数据库队列中，检查结果并控制文件增长。
- WAL 仅用于本机文件系统，不用于多机共享数据库文件；`catalog.db` 交付前应是独立可读的数据库，不依赖构建机遗留的 WAL 文件。
- 若选 WAL 且要求已成功存档的断电耐久性，使用 `synchronous=FULL`；`NORMAL` 在系统崩溃 / 断电时可能丢失最近已提交事务，不能只因性能更好便采用。

上述 WAL 行为与模式边界来自 [SQLite 官方 WAL 文档](https://www.sqlite.org/wal.html)；同步级别来自 [官方 PRAGMA 文档](https://www.sqlite.org/pragma.html#pragma_synchronous)。

### 10.3 跨平台复制与格式迁移

SQLite 数据文件可跨平台使用；实际可加载还依赖本游戏的格式、规则、定义快照与资产兼容。macOS 和 Windows 交换档案时使用已验证备份或受控导出，不能在复制时继续写原库。

格式迁移使用递增的数据库 `schema_version` 和有摘要的迁移记录，可配合 `PRAGMA user_version`；不直接修改 SQLite 内部 `schema_version`。按顺序执行、记录成功，不跳过中间步骤。对已有库采取“备份 → 临时副本迁移 → 完整性与语义检查 → 关闭连接 → 同目录替换 → 重新打开确认”的流程；原库和前置备份保留到确认成功。数据库迁移失败不以空白新库覆盖玩家进度。

客户端遇到比自身更新的格式版本只报告不支持并保留原文件；不尝试向下写入。schema 变化与数值平衡变化分开迁移；代码删除任务、装备或资产时必须给出映射 / 保留 / 明确拒绝策略。数据库文件损坏时停止写入原库并提供备份恢复，不把坏库当作首次运行重建。

## 11. 首轮实现与验收

以下是完整游戏的实现验收矩阵。已通过原生接入探针、内容检查和进度参考夹具的部分见18/22；尚未实现的真实游戏路径不能标为通过。

| 阶段 | 验证内容 | 通过条件 |
| --- | --- | --- |
| 原生接入 | 固定 Godot / 导出模板 / 插件版本；查询实际 SQLite 版本；检查 macOS arm64 与 Windows x64 debug / release | 编辑器及两个独立客户端都能打开只读定义库与用户进度库；无需朋友另装数据库服务 |
| 数值库 | 四个候选舰船定义、装备、矿物、最小任务与两个星区；约束和资源引用校验 | 错误 ID / 负数量 / 无效引用被阻止；修改数据库数值后新世界使用新值 |
| 版本冻结 | 创建旧世界后改变发布库数值并新建世界 | 旧档恢复原冻结值，新世界使用新值；同版本不同摘要能被识别 |
| 存读档闭环 | 出航、采矿、受损、任务交付、返航；手动与自动槽 | 读档后舰船、装备、库存、信用点、任务领取、星区变化与位置一致，无重复奖励 |
| 原子性 | 在状态插入、槽更新和提交附近中断进程，模拟 SQL 失败与磁盘满 | 只能得到旧完整档或新完整档；失败不显示成功，不留下可见半档 |
| 队列与读档 | 连续自动触发、手动保存、读档时旧任务回调、第二客户端占用 | 合并与优先级正确；旧会话不能覆盖新会话；忙与失败有界且可理解 |
| 备份 / 迁移 | 创建与验证备份、坏副本、未知未来格式、迁移中断 | 原库与最近有效备份保留；失败可恢复；不静默清空进度 |
| 跨平台 | 从 Mac 导出有效库，在 Windows 导入并继续；反向再测 | ID、中文文本、数值、版本和资产引用一致；无路径依赖 |
| 性能 | 真实状态量下捕获、写事务、读档、备份耗时与主线程卡顿 | 记录实测时间和峰值内存；据此决定队列、线程与自动档间隔，不预先承诺帧率 |
| 可选联机 | 房主存全体玩家、动作去重、房主读档及重连、内容不匹配 | 状态由房主一致恢复；不引入数据库共享文件或付费服务前提 |

首轮顺序：已通过的原生探针与数据材料 → Godot 单机完整快照与槽 → 真实队列/故障/备份/迁移 → 玩法闭环 → 两平台运行与交换 → 后续可选房主联机。依赖已锁定在 `code/toolchain.lock.toml`，不能把锁定等同完整功能验收。

## 12. 待实现时明确的边界

- SQLite 与 v4.9 扩展已采用并运行验证；免费授权与版本边界见22。
- 实际内嵌 SQLite 3.51.0；首版用 DELETE + EXTRA，后续升级或启用 WAL 必须重新核验修复情况。
- 槽数量、自动档间隔、是否允许战斗中保存、离线计时规则与朋友联机范围属于初版默认建议或后续玩法决定。
- 当前方案提供局部星区与完整快照的数据边界，不承担 MMO 持久化、账号服务、反作弊、云同步或自动房主迁移。
