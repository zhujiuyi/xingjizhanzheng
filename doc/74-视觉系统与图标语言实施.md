## 规范一：舰载徽记图标语言 v1

现状量化：服务图标为 24×24 viewBox、描边 1.6，实际显示尺寸与落到的像素为——飞行竖排键 18px → **1.2 px**（低于可辨认下限）、工作台侧栏 22px → 1.47 px、页头 26px → 1.73 px。这是"图标糊成灰块"的直接原因。

| # | 规则 |
| --- | --- |
| 1 | 画布 24×24 viewBox，`fill="none"`，`stroke-linecap="round"`，`stroke-linejoin="round"` |
| 2 | **描边 2.0**（原 1.6）→ 18px 显示落到 1.5 px |
| 3 | **不设装饰性外框**；统一感由系统规则承担，不由共用的装饰承担 |
| 4 | 所有符号落在同一光学区 x/y ∈ 4–20，没有哪个图标看起来更大 |
| 5 | 单色；线宽与颜色从生成脚本一处发出，15 个文件不可能各自漂移 |
| 6 | 词汇表限 45°/90°/整圆与端点圆头；舰体用箭首/梭形母题，同族的舰只靠数量区分 |
| 7 | 无填充；笔画数按可辨认优先，不设硬上限 |
| 8 | 直角，与"所有渲染按钮为直角无阴影"的既有验收一致 |
| 9 | 导入设置不变（`svg/scale=1.0`，24px 光栅落在 18–26px 显示区间内） |
| 10 | 不做 16px 简化版；按实际最小显示尺寸 18px 优化 |

**规则 3 是实测后的修订。** 第一版按"右下 45° 切角括号 + 50% 不透明度"做统一基底，渲染到 18px 后括号读起来是右下角的碎屑而不是外框，反而增加噪点——18px 下没有空间同时容纳外框和符号，"用少量墨水换统一感"的推理在真实像素上不成立。改为：统一感来自同一线宽、同一光学区、同一 45° 斜率、同一端点样式与箭首母题，不做共用装饰。首版同时暴露三处语义撞车（空间站读成放大镜、配装读成齿轮、舰队三舰糊成一团），已在第二版分别改为中心居住环、箭首入槽、箭首横列。

判定依据是逐版渲染 [code/dist 之外的对照图](../jiaoben/logs/insignia-icons-preview.png)：15 行 ×（旧 18/22/26 px | 新 18/22/26 px），由 `jiaoben/tests/insignia_icons_v3.gd` 生成，不以路径坐标代替看图。

- `code/assets/interface_v3/NotoSansCJKsc-Medium.otf`（16,523,632 字节，SHA256 `ca094f6b…d7b7`），由 editor 导入生成 `.import`，`[params]` 与 Regular 逐行一致（`diff` 为空）；导入未改动其他任何文件。
- 出处记录更新在 `sources.json`（新增 `fonts` 数组与 `glyph_coverage_note`）、`FONT_COPYRIGHT.txt`、`interface_v3/README.md`。
- 字体元数据核对：两字重均为 `Version 2.004;hotconv 1.0.118;makeotfexe 2.5.65603`；Medium 的 family 名为 `Noto Sans CJK SC Medium`（Noto CJK 每字重独立 family），本包按资源路径预加载，不做 family 查找。

**实测修正了一个错误假设。** 原方案预设"同字号换字重不改变度量"。实测（新增 `jiaoben/tests/font_metrics_v3.gd`，报告 `jiaoben/logs/font-metrics-v3.json`，**71 项通过 / 0 失败**）为：

| 项 | 结论 |
| --- | --- |
| 行高 / 上伸 / 下伸 | 两字重**完全相同**（11/13/15/20/28 px → 17/20/23/30/42） |
| 纯中文字符串步进 | **完全相同** |
| 含拉丁字母或数字的串 | Medium **宽 1–4 px**，随字号增长（8 位数字：+1 @11–13、+2 @15–20、+3 @28） |

因此换字重不改行高与中文排版，只在含数字/拉丁的串上产生几像素宽度差。依赖自动尺寸的容器不受影响；**固定宽度容器与"文字不超出控件"的验收须在改字重后复查**，该检查已写入步骤 7 的验收要求。

**字形覆盖实测**（两个字重一致）：`←` U+2190、`×` U+00D7、`…` U+2026、`·` U+00B7、`—` U+2014 **存在可用**；`▸` U+25B8、`▰` U+25B0、`✕` U+2715 **不存在**。这更正了 [73](73-界面观感与操作逻辑复审.md) EMP-03 提出的折叠指示符 `▸`——它在字体里没有字形，折叠指示改用项目既有的矢量小块 + ASCII `>` 做法。

### 步骤 6 续：按用户反馈调整目标总览与设备条

用户提出两点：目标总览的三列表头"为什么做成按钮、三个文字靠左靠右都有"；设备条"如果所有空槽都装满是不是会出现横向进度条"。

**目标总览表头**

确认那三个确实是排序按钮（`OverviewSort_distance/name/type`，点击切换排序字段与升降序），**保留排序功能**，只改样式：

- 从带底板的按钮改为**扁平列标题**：默认无边框无填充（`apply_toolbar_button`），悬停才显现，激活列用琥珀色 + 方向指示。
- 排序方向由"只给激活列追加 ` +`/` −`"改为**三列常驻一个单字符标记**（激活列 `↑`/`↓`，其余 `·`）。原来激活列的文字变宽，而距离列是右对齐的，每次排序它的标签都会横向跳动，三列看起来互不相关。

**撤回一条我自己的错误判断。** 我一度认为表头比数据列左偏 8px（推测是行按钮的内距没被补偿），并加了对应补偿；实测与既有断言证明**表头与数据列本来就是对齐的**——数据单元格挂在行按钮整块矩形上、带自己的 `ROW_INSET`，不受按钮内距影响。断言 `actual overview headers align all three contact columns` 逐列比对表头与数据格的 x 与宽度（1px 容差），我的补偿反而把它推歪并在四种尺寸上全部失败，已撤回。三列文字"靠左靠右都有"是因为距离是数值列、按列右对齐，属于表格的正确做法，不是错位。

**设备条**

用户的担心成立，且比预想更严重：目录里**最大舰体有 17 个槽位**（战列舰；巡洋舰 13）。旧设计每槽固定 80px，17 槽全装 = 1424px 挤在 656px 的容器里，一旦装满就会出现横向滚动条。改动：

| 项 | 旧 | 新 |
| --- | --- | --- |
| 行容器 | `ScrollContainer` + `HBoxContainer` | `HFlowContainer`（可换行，宽度需求恒为单个磁贴） |
| 磁贴宽度 | 固定 80（紧凑 68） | 内容宽度，最小 30 |
| 磁贴高度 | 62 | 44（紧凑 34） |
| 冷却指示 | 磁贴底部进度条 | **环绕磁贴外框的冷却环**（`SlotRing`，沿矩形周长描出剩余比例） |
| 状态文字 | 磁贴内第三行（"循环就绪"等） | 底部浮层（不占磁贴高度），只有冷却/异常态才显示文字 |
| 空槽 | 每槽一个磁贴 | 折叠为一个"空槽 ×N" |

`SlotRing` 仍暴露 `value` 与 `max_value`，语义与旧进度条相同（数据库周期长度与真实剩余秒数），依赖这两个值的既有断言不变。状态词表按磁贴宽度压到 2–3 字（损坏/锁定/缺电/受限），完整措辞保留在提示里。

**实测余量**：≥1024 宽度下 17 槽单行需 558px、可用 648–656px；640×360 逻辑尺寸下换行为两行、需 71px、可用 76px。

**新增验收守卫** `_check_equipment_row_fit`：按目录中最大槽位数（而非测试夹具的装载数）计算所需宽高并与实际可用空间比对，两种装载各一条断言。它先于修复暴露出 640×360 下两行超出 11px 的真问题——这正是"只测夹具永远测不到"的情形。同一守卫在写完当次还因把 `HFlowContainer` 按 `HBoxContainer` 取而静默返回，已一并修正为取不到即判失败。

### 步骤 8：去掉常驻服务侧栏

参考用户提供的舰船选择界面后确认的方向：**一个页面只做一件事**。服务列表原先在每一页左侧常驻 190px，重复了玩家在机库已经做过的选择，并占掉约 250px 可用宽度。改为：机库服务菜单与飞行竖排键是入口，页内只有带目的地的单一返回控件。

- 页头只剩「服务图标 + 标题 + `← 目的地`」。
- 紧凑档的服务下拉一并移除：任何尺寸下导航都走枢纽，不再有第二套模型。
- `_responsive` 原先会把页标题强制设回 25px，**静默覆盖了本轮的字阶**，已改为重新应用 `page` 角色。
- 「维修补给」补回图标（循环箭头）。它原借用配装的入槽图标，我先前直接去掉，但站内服务行"每行都有符号"是既有不变量，测试抓到了——循环箭头既表达维修补给，也不与任何图标撞车。

**测试跟着改，不是绕过去**：`service_navigation_v22` 的规范顺序断言改为从注册表的分组常量派生绘制顺序（仍是注册表事实，不是回读界面），侧栏用例重指到机库枢纽与飞行竖排键，焦点回归改为覆盖真正承担导航的返回控件；`ui_interaction_consistency` 改断言"恰好一个返回控件且写明去处"；`resource_intel_world_v26` 改由返回控件的目的地断言星图来源。

**既有失败（与本轮无关，已用干净基线逐项比对）**：`resource_intel_world_v26` 两项（F 键穿越星门、跃迁抵达声明的 AU 站点）；`navigation_commands_v6` 九项。两者在 `git stash` 干净基线上失败集合完全相同。

### 待办：舞台模式与三页重做

### 步骤 8 补：返回控件的目的地标签统一

用户反馈右上角返回控件文本不一致（"返回空间站机库"/"返回"/"返回星域航路"）。查实际渲染文本，确认是**标签与动作分两处独立计算**造成的漂移：

| 问题 | 证据 | 处理 |
| --- | --- | --- |
| 设置页写"← 返回"、不写去处 | `_close_label` 对 settings 走特例分支，`_back()` 却走 `return_page` | 两处合并为 `_back_destination()`，标签与动作**由同一函数派生**，不再可能不一致 |
| 目的地混用页面名与场景名 | 同时存在 `← 任务与合同`（页面）与 `← 空间站机库`（场景） | 保留区分，但统一形式为 `← <目的地>`；三个场景与页面在 `_destination_label` 一处命名 |

修正后 25 个页面全部为 `← 目的地` 形式，设置页从暂停进为「← 暂停与存读档」、从标题进为「← 主菜单」。

**"不同"本身是信息不是缺陷**：同一页从不同入口到达时会回到不同地方（配装分析从配装进与从暂停进），写出去处才能在视觉同形的情况下说清去向。若更想要参考图那样的纯箭头，把 `_close_label` 的返回改为固定 `"←"` 即可，提示文本仍保留目的地。
